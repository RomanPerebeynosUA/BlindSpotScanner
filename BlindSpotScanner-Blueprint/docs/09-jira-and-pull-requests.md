# 09 — Remediation: Jira tickets and fix pull requests

Both actions are **user-initiated, previewed and editable**. Nothing outward-facing happens
during a scan.

## Which items are actionable

| Source | Jira | PR |
|---|---|---|
| Endpoint `none` | ✅ | ✅ generate a new integration test |
| Endpoint `weak` / finding `FalsePositive` | ✅ | ✅ strengthen assertions in the existing test |
| Finding `SkippedTest` | ✅ | ✅ un-skip if the cause is obvious, otherwise Jira only |
| Finding `UncoveredSeam` / `Risk` | ✅ | ⚠️ only if the scope is a single test; otherwise Jira (often an epic plus sub-tasks) |
| Scorecard dimension (low score) | ✅ | ❌ |
| Bulk: "Create tickets for all untested endpoints of controller X" | ✅ (one parent plus sub-tasks) | ❌ |

## Jira ticket

- Endpoint: `POST /api/runs/{runId}/findings/{findingId}/jira-preview` → the editable draft.
  `POST …/jira` creates it.
- The ticket fields are:
  - **Summary:** `[Integration coverage] Add test for POST /orders/{id}/cancel`
  - **Description** (Markdown → ADF): the problem in plain language, why it matters, the
    detail bullets, the evidence (links to GitHub blobs at the SHA), suggested acceptance
    criteria (*"An integration test exercises POST /orders/{id}/cancel against a real DB and
    asserts the persisted status"*), and a link back to the report.
  - **Priority:** from severity (Critical→Highest, High→High, Medium→Medium, Low→Low).
  - **Labels:** `integration-coverage` plus a configurable label. Project, issue type and
    component come from Settings or a per-repo override.
- **Dedup:** before creating, look up an existing action with the same `StableKey`, and also run
  a JQL search for `labels = integration-coverage AND text ~ "<stableKey>"`. If one exists, show
  it. The stable key goes into a hidden description footer for JQL matching.
- Store `RemediationAction {Type=JiraTicket, ExternalKey, Url}`. Refresh the status lazily, on
  report view (cached for 10 minutes).
- Auth: Jira Cloud API token (email plus token) or OAuth 2.0 (3LO). The token is stored
  encrypted.

## Fix pull request

1. **Context gathering (code):** at the run's commit SHA, fetch:
   - the target controller/action source
   - 1–3 **sibling integration tests** from the same area (they show the conventions: base
     class, fixtures, client factory, DB seeding, assertion library)
   - the test project file
   - the shared fixtures
2. **Generate (LLM, `prompts/generate-fix.md`):** structured output
   `{ files: [{path, action:"create|modify", content}], rationale, assumptions[], riskNotes[] }`.
   Rules for the generated test:
   - follow the sibling conventions exactly
   - assert response **values** and **persisted state**, not just the status
   - include one failure-path test where cheap
   - no new packages unless they are already referenced
3. **Static guard (code):**
   - paths must be inside the test project
   - no edits to production code
   - file size limits
   - no secrets
   - C# files must parse (Roslyn syntax check)
4. **Preview:** show a unified diff in the UI. The user can edit the content, branch name
   (`coverage/fix-<stableKey-slug>-<shortsha>`), title and body.
5. **Create (code, GitHub REST):**
   - create the branch from the **current default branch HEAD**
   - if the target files changed since the run SHA, warn and re-run steps 1–3
   - commit the files through the Git Data API (blobs → tree → commit → ref)
   - open the PR as a **draft**
   - add the label `integration-coverage`
   - link the Jira ticket if one exists (Jira key in the title/body)
6. The PR body includes the rationale, assumptions, a link to the report, the finding, and the
   note *"Generated by Integration Coverage Analyzer — review before merging; CI must pass."*
7. Store `RemediationAction {Type=PullRequest, ExternalKey=#number, Url}`. The status (open /
   merged / closed and the checks) is refreshed lazily.

The app **does not run** the generated test. CI on the PR is the verification. A later re-scan
shows the endpoint as `newlyCovered` in the delta, which closes the loop.

## Permissions

- GitHub App (preferred) scopes: `contents:read` for scanning. `contents:write` and
  `pull_requests:write` are needed only if PR creation is enabled.
- A read-only mode (no write scopes) hides the PR buttons.
