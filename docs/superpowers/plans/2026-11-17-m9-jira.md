# M9 Jira Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Create a Jira ticket from a report finding through an editable preview, never twice for the same stable key, and show each ticket's live status on the report.

**Architecture:**
- A typed `JiraClient` (Infrastructure, HttpClient plus Basic auth) does three REST calls: create, JQL search and get status.
- `JiraTickets` (Application) builds the draft from the stored report, dedups against stored actions and then JQL, creates the ticket and stores a `RemediationAction`.
- A small Markdown→ADF converter turns the edited description into Atlassian Document Format on the server.
- `GET /api/repositories/{id}/actions` lists the actions and refreshes Jira statuses older than 10 minutes.
- The web app gets a Jira dialog, buttons on findings and untested endpoint rows, ticket links, and the Actions log.

**Tech Stack:** .NET 10, EF Core 10 + Npgsql, WireMock.Net, xUnit + FluentAssertions 7; Angular 22 + Angular Material dialog, Vitest, Playwright.

**Spec:**
- `BlindSpotScanner-Blueprint/docs/09-jira-and-pull-requests.md` ("Which items are actionable", "Jira ticket");
- `docs/04-frontend-angular.md` ("Jira dialog", report sections 4, 6 and 7);
- `docs/10-security-config-ops.md` (Jira config, secrets);
- `docs/11-implementation-plan.md` M9;
- the user's M9 answers, recorded as D24 in Task 1.

## Global Constraints

- M9 AC: "WireMock Jira tests assert the exact REST payload (ADF), and dedup prevents a second ticket."
- Summary: `[Integration coverage] Add test for <METHOD route>` for an uncovered endpoint (doc 09 example: `[Integration coverage] Add test for POST /orders/{id}/cancel`).
- Priority from severity: Critical→Highest, High→High, Medium→Medium, Low→Low.
- Labels always include `integration-coverage`, plus the configured `Jira:Labels`.
- Dedup: a stored action with the same `(RepositoryId, StableKey)` and type JiraTicket, then JQL `labels = integration-coverage AND text ~ "<stableKey>"`. The stable key goes into a description footer.
- Ticket status is refreshed lazily on report view, cached for 10 minutes.
- Principle 8: nothing outward-facing without a human click after a preview. Principle 9: the Jira token never appears in logs, errors or API responses.
- Config only (D24): `Jira:BaseUrl`, `Jira:Email`, `Jira:ApiToken` (user secrets or env vars, never appsettings), `Jira:ProjectKey`, `Jira:IssueType` (default `Task`) and `Jira:Labels` (default `["integration-coverage"]`). No settings page.
- Scope (D24): Jira buttons on the Findings section and on untested endpoint rows only. Top risks, scorecard rows and bulk epics are out of scope.
- WireMock only; no live Jira test (D24).
- Tests are named `Method_Scenario_ExpectedResult` and use Arrange/Act/Assert comments, one behavior each.

## Review Focus

1. **Jira is down or rejects the token during a status refresh.** The actions list still returns the last known status; the report never fails because of Jira. Test: `ActionsAsync_JiraFails_KeepsCachedStatus` (Task 4).
2. **Stable keys with JQL-special characters** (`uncovered-endpoint:POST api/orders/{}/cancel`). The search must not error, and a fuzzy hit counts as a duplicate only when its description footer holds the exact key. Tests: `FindByStableKeyAsync_EscapesSpecialCharacters` and `FindByStableKeyAsync_FuzzyHitWithOtherKey_ReturnsNull` (Task 3).
3. **The user deletes the footer or the `integration-coverage` label while editing.** The server always appends the footer and adds the label, so dedup still works later. Test: `CreateAsync_EditedDraftWithoutLabel_StillSendsLabelAndFooter` (Task 4).
4. **Jira is not configured.** Preview and create return 503 with a ProblemDetails message naming the missing settings, and the UI shows it as a snackbar. Test: `Preview_JiraNotConfigured_Returns503` (Task 5).
5. **The token leaks through an error message.** Jira's 401 and 400 bodies become a `JiraException` whose message never contains the token or the Authorization header. Test: `CreateIssueAsync_Unauthorized_ThrowsWithoutToken` (Task 3).

### Task 2: Markdown → ADF

**Files:**
- Create: `src/BlindSpotScanner.Infrastructure/Jira/AdfConverter.cs`
- Test: `tests/BlindSpotScanner.Infrastructure.Tests/Jira/AdfConverterTests.cs`

**Interfaces:**
- Produces: `public static JsonObject AdfConverter.ToAdf(string markdown)` returns `{"type":"doc","version":1,"content":[…]}`.

**Rules** (the whole supported subset; everything else is plain text):
- `## Heading` becomes `{"type":"heading","attrs":{"level":2},"content":[inline]}`. The same applies to `#` and `###` with levels 1 and 3.
- A run of `- item` lines becomes one `{"type":"bulletList","content":[{"type":"listItem","content":[{"type":"paragraph","content":[inline]}]}…]}`.
- Other non-blank lines form paragraphs, separated by blank lines. Consecutive lines in a paragraph are joined with `{"type":"hardBreak"}`.
- Inline: `[text](url)` becomes `{"type":"text","text":"text","marks":[{"type":"link","attrs":{"href":"url"}}]}`, and `` `code` `` becomes `{"type":"text","text":"code","marks":[{"type":"code"}]}`. Plain runs become `{"type":"text","text":"…"}`. Empty text nodes are never emitted (Jira rejects them).
- `\r\n` is treated as `\n`.

    - `Task<JiraIssueRef> CreateIssueAsync(JiraIssueRequest request, CancellationToken ct)`; the returned status is `"To Do"` (Jira's create response has no status).

**REST shapes** (Jira Cloud v3, checked in context7):
- **Create:** `POST /rest/api/3/issue` with body
  `{"fields":{"project":{"key":P},"issuetype":{"name":T},"summary":S,"description":<ADF>,"priority":{"name":Pr},"labels":[…]}}`.
  - The description is `AdfConverter.ToAdf(markdown + "\n\nBlindSpotScanner key: " + stableKey)`.
  - The `201` response is `{"id","key","self"}`; the URL is `{BaseUrl}/browse/{key}`.
- **Search:** `POST /rest/api/3/search/jql` with body `{"jql":…,"fields":["status","description"],"maxResults":10}`.
  - The response is `{"issues":[{"key","fields":{"status":{"name"},"description":<ADF>}}]}`.
  - JQL: `labels = integration-coverage AND text ~ "<phrase>"`. The phrase is the stable key with every character outside `[A-Za-z0-9 ]` replaced by a space and runs of spaces collapsed.
  - A hit counts only when some text node of its description equals `BlindSpotScanner key: <stableKey>`.
- **Status:** `GET /rest/api/3/issue/{key}?fields=status` returns `fields.status.name`.
- **Auth:** `Authorization: Basic base64(email:token)` and `Accept: application/json`, set per request. Any non-success status throws `JiraException($"Jira returned {code} for {operation}")` with Jira's `errorMessages` appended, never the token or the header.

**Draft content:**
- **Summary:**
  - UncoveredEndpoint: `[Integration coverage] Add test for {Detail[0]}`;
  - every other kind: `[Integration coverage] {Headline}`.
- **Priority:** `Severity.ToString()`, except Critical, which becomes `Highest`.
- **Labels:** `defaults.Labels` with `integration-coverage` first and no duplicates.
- **Description Markdown** (sections in this order; an empty section is left out):

```
## Problem
{Headline}

## Why it matters
{WhyItMatters}

## Details
- {each Detail}

## Evidence
- [{citation}]({repo.HtmlUrl}/blob/{meta.CommitSha}/{path before "::"})

## Acceptance criteria
- {by kind, below}

[View the report]({PublicUrl}/runs/{runId})
```

- **Acceptance criteria by kind:**
  - UncoveredEndpoint: `An integration test exercises {Detail[0]} against a real database and asserts the response values and the persisted state.`
  - WeakTest and FalsePositive: `The test asserts response values and persisted state, not only the status code.`
  - SkippedTest: `The test runs (is not skipped) and passes in CI.`
  - UncoveredSeam: `At least one integration test crosses this seam for real instead of a fake.`
  - Risk: `The risk is covered by an integration test or accepted with a written reason.`

**Behavior:**
- **Preview:**
  - an unknown run or finding id gives `NotFound`;
  - a run that isn't Succeeded gives `NoReport`;
  - Jira not configured gives `NotConfigured`;
  - otherwise the draft, with `Existing` set to `FindActionAsync(…, JiraTicket)`. The preview makes no Jira call.
- **Create:**
  - It checks the same three outcomes as preview.
  - Unless `Force`, a stored action means `Exists`. Otherwise, if `FindByStableKeyAsync` finds a ticket that isn't stored, the ticket is stored as an action (adopted) and the result is `Exists` with it.
  - Otherwise: `EnsureFindingAsync`, then `CreateIssueAsync` with the request's labels plus `integration-coverage` and the finding's stable key, then store `RemediationAction { Type = JiraTicket, ExternalKey = key, Url, Status, StatusCheckedAt = now, CreatedBy = "anonymous" }`, then `Ok`.
- **Actions:**
  - Jira actions with `now - StatusCheckedAt >= 10 minutes` get `GetStatusAsync`.
  - On success, update `Status` and `StatusCheckedAt`. On `JiraException` or `HttpRequestException`, keep the old status.
  - Save once, then return the list.
